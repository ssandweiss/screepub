# The proof sheet: one torture fixture, and the kit around it

An invented screenplay PDF of 13 body pages plus a title page, 14 sheets
in all, that exercises every content-driven behavior in
`docs/formatting-options-log.md`, generated by
`tools/make-fixture.py`, committed to `tests/fixtures/`, and guarded by a
coverage check that fails when a new registry entry has no decision
attached to it.

## Why

Screepub has 33 registry entries and four device verdicts still pending
(#16, #8c, #10b, #17). The committed fixtures cannot settle any of them:
`screenplay.pdf` is a clean, well-behaved script that covers the happy
path, and the two guard fixtures are deliberately not screenplays. Real
scripts can settle them, but they live in the gitignored `/fixtures/`,
never run in CI, and cannot appear in a bug report, a doc, or a
screenshot.

So the project has no artifact that is both hostile enough to prove
anything and safe enough to commit. This is that artifact.

It has two jobs, in this order:

1. **A device pass.** Convert it, copy it to a Kindle, and look at it.
   Every test case announces itself on the page, so a defect is findable
   on a six-inch screen and quotable in a registry verdict.
2. **A regression suite.** Source-side behavior gets asserted in
   `bun test`, so the fixture keeps proving things long after the device
   pass that motivated it.

Job 1 comes first because job 2 is worthless if nobody ever looks at the
output, and because the immediate need is a 0.5.0 device pass.

## The two physics

The fixture tests two different systems that fail in different ways, and
conflating them produces tests that cannot work.

**Source-side, the parser.** The generator controls pagination to the
line. Page furniture, `(MORE)`/`(CONT'D)` rejoin across a break,
page-number markers and Final Draft double-print dedup can all be
engineered exactly and asserted deterministically.

**Device-side, the renderer.** The EPUB is reflowable. The device decides
where pages break from its own font size, screen dimensions and margins.
Nothing in the source PDF can pin an output page boundary.

Device-side coverage is therefore **saturation, not precision**: a
passage dense with the pattern under test, repeated enough that at any
plausible font size some instance straddles a boundary. Changing the
Kindle's font size re-rolls every break point, which turns one PDF into
many trials.

This is why the page budget splits roughly 60/40 between variety and
saturation. A pure variety catalog would be denser and would prove less.

## Evidence: the font spike

The rich-formatting page rests on pdf.js reporting a usable PostScript
name for **non-embedded** base-14 fonts. Real scripts embed fonts named
like `CourierPrime-Italic`; ours would not embed anything. If pdf.js
reported an internal name such as `g_d0_f2`, the regex in
`src/parser/extract.ts` (`/bold|black|heavy/i`, `/italic|oblique/i`)
would match nothing, every styled item would come back plain, and the
fixture would "pass" while proving the opposite of what it claims.

A throwaway two-page PDF using `Courier`, `Courier-Bold`,
`Courier-Oblique` and `Courier-BoldOblique`, run through
`bun src/cli.ts`, produced:

```
This action has a **bold** word in it.
This action has an *italic* word in it.
This one is ***bold italic*** together.
This action has an underlined word drawn as vector art.
```

**Result: base-14 works. No font embedding needed**, and the generator
stays a pure-Python string builder with no new dependencies.

The fourth line is the other half: the vector underline was drawn and
came through completely plain, confirming registry 9d's recorded
limitation and establishing the expected-fail baseline before any of the
real fixture exists.

## The generator

Four changes to `tools/make-fixture.py`, each isolated from the code path
that produces the three existing fixtures.

### 1. Styled runs via inline markup

Content stays readable as prose, which matters because 13 pages of it get
hand-edited:

```python
("action", "She reads the sign: {b}EVERYTHING MUST GO{/b}, in {i}her{/i} hand.")
```

`{b}`, `{i}` and `{u}` parse into runs at layout time. `{b}`/`{i}` select
among four Type1 font resources; `{u}` additionally emits a filled
rectangle (see 3).

### 2. An offset-preserving wrapper, used only by the torture kind

`textwrap.wrap()` takes a plain string, so markup embedded in the text
would have its characters counted as width and could be split across a
line boundary. Instead: strip markup to plain text plus character spans,
wrap the plain text while tracking offsets, then re-intersect the spans
per wrapped line.

**The existing three kinds keep calling `textwrap` untouched.** That
decoupling is deliberate: it means the byte-stability guard can never
fail because of a wrapper change, which would be a false alarm about a
real risk.

### 3. Vector underlines

`{u}` runs emit a filled rectangle roughly 0.6pt tall, about 2pt below
the baseline, spanning the run's width. Those dimensions are chosen to
satisfy the detection criteria the rich-formatting spec proposes (flat
bbox under 2.5pt, width at least 4pt, under 85% of page width, matched
within a band of the baseline), so that when phase 1 is implemented this
fixture is already its acceptance test.

### 4. Explicit pagination directives

Source-side tests need lines placed exactly:

```python
("atline", 50),            # pad to line 50 of the current page
("character", "MARGO"),    # so this speech straddles the break
("dialogue", "..."),       # and triggers (MORE) / (CONT'D)
("pagebreak", ""),
```

`atline` **raises if the page is already past the requested line** rather
than silently overflowing. Otherwise adding a sentence on page 4 would
quietly move the boundary and turn the `(MORE)` test into a test of
nothing. Silent decay of that kind is what makes old fixtures
untrustworthy.

### 5. Two-column placement for dual dialogue

Emits two cue-shaped clusters on one Y line, then partitions body lines
by start-x, which is what `deinterleaveDualDialogue` keys on (registry
10a: the boundary starts at `rightCueX - 13%` and refines leftward).

Two exchanges are required, not one: entry 10b falls back to sequential
above 12 estimated rendered lines, so a single short exchange would leave
half the behavior unexercised.

## The kit

`tools/torture-manifest.json` is the single source of truth, with one row
per registry entry:

```json
{ "entry": "9d", "title": "Inline bold/italic pass-through",
  "covered": true, "page": 6, "side": "source",
  "how": "bold, italic and bold-italic runs in action and dialogue" }

{ "entry": "14", "title": "Scanned-PDF bail-out",
  "covered": false,
  "why": "a screenplay fixture cannot also be a scanned page; blank-pages.pdf owns this" }
```

The `side` field (`source` | `device` | `both`) is what lets one file
serve both halves: `source` entries are provable by machine, `device`
entries can only be looked at.

Three consumers:

1. **`tests/torture-coverage.test.ts`** parses the `###` headings out of
   the registry and asserts every one has a manifest row. It does not
   require `covered: true`, only that somebody decided. A new entry 18
   with no row fails the suite.
2. **`tests/torture.test.ts`** holds source-side assertions for
   `side: source` and `both`: element type counts, `styledText`
   contents, dual-dialogue de-interleaving, `(MORE)`/`(CONT'D)` rejoin,
   scene numbers.
3. **`bun tools/device-checklist.ts`** prints a markdown checklist of
   every `side: device` entry, to carry to the Kindle. Generated rather
   than hand-maintained so it cannot drift from the manifest.

### The byte-stability guard

A test regenerates `screenplay.pdf`, `prose.pdf` and `blank-pages.pdf`
and asserts the bytes match what is committed. This is what makes it safe
to extend the shared generator rather than forking a second one.

It makes `python3` a hard dependency of the engine test suite. That is
accepted deliberately. A skip-if-missing guard is explicitly rejected:
this repo already fixed exactly that failure, where integration tests
self-skipped and therefore never ran in CI. A test that quietly skips is
worse than one that was never written, because it reads as coverage.

The plan must verify `python3` is present on the CI runner images rather
than assume it.

### Expected-fail assertions

Behavior that is specified but unbuilt is included and asserted at its
current wrong answer:

```ts
// Registry 9d: underline is drawn as vector art, not font data, so it is
// NOT detected. Rich-formatting phase 1 changes that. When it lands, this
// assertion fails, and that failure is the signal to flip it, not a bug.
expect(styled).toBe("This action has an underlined word drawn as vector art.");
expect(styled).not.toContain("_");
```

The first line matters as much as the second. Asserting only the absence
of `_` would also pass if the sentence vanished entirely, so a regression
that dropped the text would look like success.

### Device results

They feed the registry's existing `Device verdict: pending` slots. No new
bookkeeping: #16, #8c, #10b and #17 already have those slots waiting, and
this fixture is how they get filled.

## Risks

- **`atline` conflicts.** Content edits can push a page past a requested
  line. Mitigated by raising rather than overflowing, so the failure is
  loud and local.
- **Saturation may not saturate.** If the device's page height happens to
  align with the repeated pattern's period, breaks could land in the same
  relative position every time. Mitigated by varying speech lengths
  within the saturation pages rather than repeating one uniform shape.
- **The byte-stability guard could fail for benign reasons**, for example
  a Python version difference in dict ordering or float formatting. If
  that appears, the fix is pinning the formatting in the generator, not
  loosening the assertion.

## Out of scope

- Implementing underline detection. This fixture generates its input and
  asserts its current absence; the rich-formatting spec owns the feature.
- Replacing `screenplay.pdf`. It stays as the clean happy-path fixture.
- A second non-screenplay fixture. `prose.pdf` and `blank-pages.pdf`
  already cover the guards.
- Automating the device pass. It is a human looking at a Kindle, and the
  checklist is the only tooling proposed.
